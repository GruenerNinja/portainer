# Changing the Vault integration

Use this file as the change map when extending or repairing the integration.

## API schema and client generation

The API contract has four layers that must agree:

1. Go source types, payload structs, and Swagger annotations.
2. `api/docs/swagger.yaml` generated by `swag`.
3. `api/docs/openapi.yaml` converted from Swagger.
4. TypeScript types, SDK functions, and Zod runtime validators under `app/react/portainer/generated-api/portainer/`.

After changing layer 1, run from the repository root:

```sh
make generate-api
git diff --check
```

Commit the relevant changes from all four layers. Generated files must not be patched manually because the next generation removes the patch.

For a source type change, verify both representations:

- `portainer.SourceType` in `api/portainer.go` is the persisted numeric enum. Append new values; reordering existing values changes stored data semantics.
- `sources.SourceType` in `api/http/handler/gitops/sources/types.go` is the public string enum. Update its constants, parser, and conversion switch.

For Vault specifically, the generated results must contain:

```ts
z.enum(['git', 'helm', 'oci', 'vault']);
```

in `zSourcesSourceType`, and the list query enum must also include `vault`. The generated SDK should contain the Vault create and pre-save test operations. Run `make docs-sync-check` in CI or before merging to catch Go-to-Swagger drift.

## Adding or changing Vault configuration fields

Update all applicable locations:

1. Stored model: `VaultConfig` or `VaultAuthentication` in `api/portainer.go`.
2. Create payload, validation, defaults, and model conversion in `create_vault.go`.
3. Pointer-based update payload and merge behavior in `update_vault.go`. Pointers distinguish “not supplied” from a zero value.
4. Sanitized response DTO in `get.go`. Do not expose credentials.
5. Connection testing and real Vault requests in `api/gitops/secrets/vault.go`.
6. Create/edit form values, validation, payload conversion, and request hooks under `app/react/portainer/gitops/sources/`.
7. Swagger annotations and generated artifacts via `make generate-api`.
8. Backend and frontend tests listed in [Testing](testing.md).

If a new credential is added, redact it on every response path and decide how an omitted update value preserves the existing secret. Never return a stored credential merely to repopulate an edit form.

## Adding an authentication method

Token auth is currently assumed in validation, payload defaults, form state, edit UI, display UI, and `applyVaultHeaders`. A new method therefore requires more than adding a header:

- Define a discriminated configuration shape and validation rules.
- Keep stored credentials backward-compatible.
- Add create and partial-update payload behavior.
- Update request construction in the Vault client.
- Update create/edit/test UI and avoid exposing stored secrets.
- Add redaction and serialization tests for every credential field.
- Add connection and secret-read tests using an HTTP test server.
- Regenerate the API client and validators.

Prefer a dedicated authentication abstraction before adding several methods; scattered method checks are easy to miss.

## Changing KV paths or folder expansion

Keep path construction in `api/gitops/secrets/vault.go`. Callers pass a logical path containing the mount, without `/v1/`. Test all of these cases:

- KV v1 read.
- KV v2 read with and without an already supplied `data/` segment.
- KV v2 list with and without an already supplied `metadata/` or `data/` segment.
- `LIST` success and `GET ?list=true` fallback.
- Empty paths, missing keys, non-2xx responses, malformed JSON, and nested folders.
- Folder children containing one value and several values.

If naming rules change, treat that as a user-visible compatibility change: generated environment variable names may be consumed by existing Compose files.

## Changing stack secret mappings

Update the stored `StackSecretMapping` model, create/update API payloads, frontend mapping type, create-stack payload mapper, edit-stack payload mapper, validation, and the fieldset UI together. Regenerate the API contract whenever a Go payload or model changes.

Every deploy path must resolve mappings before deployment. Search for `stackWithResolvedSecrets` and confirm new deployer entry points call it. Keep resolution on a copy so resolved secret values are not persisted in the stack record.

## Adding another secret provider

Do not overload Vault-specific fields. Add an explicit source type and provider configuration, then refactor the deployment resolver behind a provider interface. Preserve source authorization, response redaction, timeouts, error context, and deterministic environment insertion. Update both source type enums and regenerate the entire API contract.
